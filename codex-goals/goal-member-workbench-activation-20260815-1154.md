# Codex Goal Contract — 회원용 주식 워크벤치의 첫 분석 완료 흐름

이 파일은 완전한 영속형 목표 계약서다. 작업 전에 전체를 읽고, 이전 채팅 기록에 의존하지 말며, 아래 완료 조건이 충족되거나 하드 일시정지 조건이 발생할 때까지 자율적으로 진행한다.

## Goal

Jay AI Platform에서 일반 회원이 로그인한 뒤 한국 주식 워크벤치에 진입하여 보유종목 또는 관심종목을 등록하고, 첫 분석을 실행해 저장된 결과와 다음 행동을 확인하는 흐름을 명확하고 안정적으로 완성한다. 대표 전용 YouTube·이모티콘 콘텐츠 운영 도구는 일반 회원의 핵심 제품 흐름과 분리된 관리자 영역으로 유지한다.

## User problem and value

- **주 사용자:** 한국 주식을 기록하고 분석 결과를 다시 확인하려는 일반 회원.
- **사용 상황:** 회원가입 또는 로그인 후 자신의 종목을 등록하고, 분석 결과를 저장해 재방문 때 이어서 검토한다.
- **핵심 문제:** 현재 제품에는 인증, 포트폴리오, 관심종목, 분석, 공시, 결제, 콘텐츠 운영 기능이 함께 존재하지만 일반 회원의 첫 분석 완료까지의 진입 경로와 콘텐츠 운영 도구의 경계가 제품 약속으로 고정되어 있지 않다.
- **완료 가치:** 회원은 어디서 시작해 무엇을 입력하고 어떤 결과를 얻는지 혼동하지 않으며, 대표는 회원 제품과 관리자 전용 운영 도구를 구분한 채 첫 활성화 흐름을 검증할 수 있다.
- **가장 중요한 현재 공백:** 기능 존재 자체는 확인되지만, 첫 분석 완료라는 대표 사용자 가치와 재방문 가능한 저장 결과를 하나의 검증된 흐름으로 보장하는 정보 구조·권한·오류 상태가 아직 확정되지 않았다.

### Inferred

- 가장 작은 사용자 가치 검증 단위는 결제나 AI 외부 API가 아니라, 저장된 주식 입력에서 분석 결과를 확인하고 다시 열어보는 로컬 규칙 기반 흐름이다.
- 콘텐츠 운영을 일반 회원 메뉴에서 완전히 제거할지, 관리자 전용 섹션으로 유지할지는 기존 검토의 선택지 A/B 중 대표가 승인해야 하는 제품 정책이다. 기본 권고는 관리자 전용 유지다.

### Unknown

- 현재 작업 트리의 `App.tsx` 변경이 어느 정도까지 회원/관리자 내비게이션과 첫 분석 흐름을 이미 반영했는지 알 수 없다. 구현 전에 `git diff -- frontend/src/App.tsx frontend/src/App.test.tsx`와 관련 컴포넌트·API를 읽어 확인한다.
- 현재 로컬 개발 서버와 브라우저에서 실제 회원의 첫 분석 흐름이 어느 지점에서 끊기는지 알 수 없다. 별도 임시 데이터 디렉터리로 로컬 서버를 실행하고 실제 UI 진입점에서 확인한다.
- 대표가 콘텐츠 운영을 관리자 전용으로 유지하는 권고를 승인했는지는 알 수 없다. 이 정책이 일반 회원의 메뉴·라우팅·권한 계약을 바꾸는 단계에 도달하면 대표 승인 전에는 구현을 확정하지 않는다.

## Constraints

### In scope

- 현재 코드와 작업 트리를 조사해 일반 회원의 첫 분석 완료 흐름과 관리자 전용 콘텐츠 운영 경계를 확정한다.
- 필요한 경우 회원용 기본 내비게이션, 주식 입력·분석·저장 결과 화면, 로딩·빈 상태·오류 상태, 관리자 콘텐츠 운영 진입 경로를 최소 범위로 수정한다.
- 기존 인증·권한·분석 사용량 제한·저장 데이터 의미를 보존하고, 결함이 드러날 때 실제 사용자 흐름을 재현하는 최소 회귀 테스트를 추가한다.
- SQLite 스키마가 정말 필요할 때만 기존 `services/*.py` 패턴과 무손실 확장 원칙을 따른다.
- 브라우저 또는 가장 가까운 실제 UI 인터페이스를 통해 대표 흐름을 검증하고, 변경 범위에 맞는 pytest, `ruff check backend`, `cd frontend; npm run verify`를 실행한다.

### Explicit non-goals

- Toss 결제 실결제, OpenDART 운영 키, OpenAI 실 API, Yahoo Finance 운영 데이터, VPS 배포, 운영 DB 변경은 이 Goal의 범위가 아니다.
- 새로운 리포트 마켓, 구독 가격 정책, B2B 기능, YouTube·이모티콘 콘텐츠 제작물 제출은 구현하지 않는다.
- `AI_COMPANY*.md`, `MY_COMPANY*.md` 원본 템플릿은 수정하지 않는다.
- 프론트엔드 또는 문서에 이미 존재하는 사용자 변경을 되돌리거나, 테스트를 약화하거나 삭제해 통과시키지 않는다.
- 사용자 승인 없이 commit, push, PR, merge, 배포를 수행하지 않는다.

### Protected rules

- `.env`, `.env.production`, SSH 키, 토큰, API 키, 개인정보, 실제 사용자 데이터와 `backend/data/*.db` 원본을 읽거나 결과에 포함하지 않는다.
- 임시 검증은 명시적으로 별도 `DATA_DIR`를 사용해 실제 사용자 DB와 격리한다. 임시 DB와 테스트 산출물은 기존 보호 경계를 벗어나 삭제하지 않는다.
- 배포 스크립트(`scripts/deploy-vps.ps1`, `deploy-ubuntu.sh` 등)는 실행하지 않는다.
- 코드 변경이 생기면 `frontend/`와 `backend/`의 소유권·검증 범위를 확인하고, 루트 `AGENTS.md`/`CLAUDE.md`는 수정하지 않는다.
- 외부 서비스 호출이 필요한 기능은 자격 증명 없이도 재현 가능한 로컬 경로를 우선 검증한다. 자격 증명 설정을 요구하거나 비밀값을 출력하지 않는다.

## Done when

대표 사용자 흐름이 실제 로컬 UI에서 **AND** (1) 일반 회원이 로그인 후 회원용 주식 워크벤치에 명확히 진입하고, (2) 보유종목 또는 관심종목을 입력·저장하고, (3) 분석을 실행해 점수/신호/위험/요약 등 실제 응답 결과를 확인하고, (4) 저장된 분석 결과 또는 이력으로 재방문 가능한 상태를 확인하며, (5) 일반 회원에게 대표 전용 콘텐츠 운영 기능이 노출되지 않고 관리자 계정에서는 권한에 맞는 운영 진입이 확인되고, (6) 변경 범위에 맞는 테스트와 정적·빌드 검증이 실제로 실행되어 통과할 때 이 Goal을 완료한다.

- **대표 real user flow:** 별도 임시 데이터 디렉터리로 로컬 백엔드·프론트를 실행 → 첫 가입 계정 또는 테스트 회원으로 로그인 → Korea Stocks 진입 → 종목 입력/저장 → AI Analysis 또는 해당 분석 진입 → 분석 실행 → 결과·이력 재확인. 별도로 관리자 계정으로 로그인해 Content Ops가 관리자 전용으로만 보이는지 확인한다.
- **정확한 관찰 결과:** 회원 화면에 첫 분석을 완료할 수 있는 시작점과 다음 행동이 표시되고, 입력한 종목의 저장 결과와 분석 결과가 화면에 남으며, 새로고침 또는 이력 재진입 후에도 확인된다. 비관리자에게 Content Ops API/UI가 노출되지 않고 관리자에게만 허용된 응답과 화면이 표시된다.
- **증거:** 브라우저 관찰 메모 또는 스크린샷, 관련 API 응답 상태, 실행한 명령과 결과, 변경 파일 목록, 필요한 경우 임시 DB 확인 결과를 남긴다. 비밀값과 실제 사용자 데이터는 기록하지 않는다.
- **검증 명령:** 최소 `python -m pytest`, `ruff check backend`, `cd frontend; npm run verify`를 변경 범위와 프로젝트 정책에 맞게 실행한다. 실행하지 않은 검사를 통과했다고 보고하지 않는다.
- **회귀 경계:** 기존 회원가입·로그인·로그아웃, 관리자 권한 보호, 주식 입력/분석의 기존 계약, 콘텐츠 운영의 비관리자 차단, 빌드가 깨지지 않아야 한다.
- **허용된 잔여 한계:** 외부 시장 데이터·OpenAI·Toss·OpenDART 키가 없는 로컬 환경에서는 해당 외부 연동의 실서비스 성공을 주장하지 않는다. 대신 로컬 규칙 기반 분석과 명확한 미설정 상태만 검증한다.

## Execution checkpoints

1. **현재 작업과 실제 진입 경로 재구성** — `AGENTS.md`, `README.md`, 기존 검토 문서, 현재 `git diff`, 주식·인증·콘텐츠 운영 코드와 테스트를 읽고 현재 회원/관리자 흐름 지도를 만든다. 증거는 파일 경로, 테스트 목록, 현재 diff다. 다음 단계로 가려면 기존 변경을 보존하면서 변경 지점과 실제 미완성 지점을 구분해야 한다.
2. **정책 경계 확인** — 회원 기본 메뉴와 관리자 콘텐츠 운영의 현재 동작을 로컬 임시 환경에서 확인하고, 기존 검토의 관리자 전용 권고를 적용할지 대표 승인 필요 여부를 기록한다. 회원 메뉴·라우팅 정책을 바꾸는 선택이 승인되지 않았으면 여기서 하드 일시정지하고, 구현을 강행하지 않는다.
3. **첫 분석 완료 흐름 구현** — 승인된 범위 안에서 가장 작은 변경으로 회원의 주식 입력 → 분석 실행 → 결과 저장/이력 재진입을 연결하고, 로딩·빈 상태·실패 상태를 사용자에게 이해 가능한 문구로 보장한다. 증거는 변경 파일과 최소 회귀 테스트다. 다음 단계로 가려면 코드 경로가 기존 인증·사용량 제한·데이터 저장 계약을 깨지 않아야 한다.
4. **관리자 경계와 회귀 검증** — 일반 회원과 관리자 각각의 실제 UI 흐름을 실행하고 권한 경계·기존 기능 회귀를 확인한다. 증거는 브라우저 관찰 및 API 응답, 관련 pytest 결과다. 다음 단계로 가려면 대표 real user flow가 코드 내부 테스트만이 아니라 실제 진입점에서 성공해야 한다.
5. **전체 검증과 인수 산출물 정리** — 필요한 전체 pytest, `ruff check backend`, `cd frontend; npm run verify`를 실행하고 변경 파일·검증 결과·잔여 한계를 정리한다. 증거는 명령 원문과 실제 결과다. 모든 `Done when` 절이 충족될 때만 완료 보고를 한다.

체크포인트 순서는 새 증거가 기존 가정을 반박하면 수정할 수 있으며, 수정 이유를 진행 로그에 남긴다. 읽기 중심 조사는 병렬화할 수 있지만 같은 파일을 쓰는 작업은 소유권이 충돌하지 않을 때만 병렬화한다.

## Autonomous decision contract

- 사용자가 자리를 비웠다고 가정하고 routine하고 되돌릴 수 있는 결정은 멈추지 않고 진행한다.
- 판단은 이 Goal, 사용자 가치, 현재 코드, 프로젝트 정책, 기존 설계, 테스트, 실제 런타임 증거와 커밋 이력을 근거로 한다.
- 되돌릴 수 있는 선택은 즉시 실행하되, 기존 제품 방향에 맞는 가장 안전하고 유지보수 가능한 선택을 우선한다.
- 한 경로가 막혀도 공유 원인이나 중대한 안전 위험이 아니라면 독립 조사를 계속한다.
- 사용자의 권한을 만들어내지 않는다. 이 Goal은 워크스페이스 조사, 범위 내 구현, 관련 테스트와 문서화를 허용하지만 commit, push, PR, merge, 배포, 운영 변경은 별도 승인 없이는 허용하지 않는다.
- 접근권한·자격증명·인프라가 없어 수행할 수 없는 행동을 성공했다고 보고하지 않는다.
- 기존의 유효한 미커밋 작업을 보존하고 통합한다. 단순화를 위해 삭제·덮어쓰기·초기화하지 않는다.
- 성공처럼 보이게 하려고 테스트·보안·리뷰·CI·배포 통제를 삭제하거나 약화하지 않는다.

## Recursive improvement and failure recovery

Goal과 권위 있는 출처 집합은 고정하지만, 가설·분해·구현 전략·검증 전략은 새 증거에 따라 수정한다. 이 Goal을 처음 실행할 때 이전 실패는 확인되지 않았으므로 실패 이력을 발명하지 않는다.

체크포인트가 실패하거나 같은 목표가 이미 저항한 증거가 나오면 다음 순서로 회복한다.

1. 반복된 가정, 빠진 증거, 실제 사용자 흐름을 우회한 검증 경로를 식별한다.
2. 다음처럼 메커니즘이 다른 최소 세 가지 접근을 비교한다.
   - **접근 A — 단일 회원 워크벤치 집중:** 일반 회원의 기본 화면과 주식 분석 흐름을 먼저 단순화하고 관리자 콘텐츠 운영은 별도 진입으로 이동한다. 예상 성공 가능성은 중간~높음(약 60~75%)이며 현재 코드·제품 검토의 권고와 가장 직접적으로 맞는다.
   - **접근 B — 역할별 셸 분리:** 인증 직후 역할별 앱 셸·라우팅·내비게이션을 분리하고 각 셸 안에서 기존 기능을 재배치한다. 예상 성공 가능성은 중간(약 45~65%)이며 경계는 선명하지만 현재 변경량과 회귀 표면이 커진다.
   - **접근 C — 기존 화면 유지 + 단계별 온보딩:** 정보 구조를 크게 바꾸지 않고 첫 분석 CTA, 안내, 빈 상태와 이력 연결을 추가한다. 예상 성공 가능성은 중간(약 40~60%)이며 구현 비용은 낮지만 콘텐츠 운영과 회원 제품의 구조적 혼재를 남길 위험이 있다.
3. 가장 적은 비용으로 가장 많은 정보를 주는 실험을 선택하고, 가능한 경우 실제 제품 진입점에서 실행한다.
4. 각 반복 후 새로 확인된 사실, 틀린 가정, 전제가 바뀌지 않으면 반복하지 않을 방법, 현재 최대 병목, 다음 최고 정보량 실험을 진행 로그에 기록한다.
5. 실패하면 같은 방법을 더 강하게 반복하지 말고 관찰된 원인에 맞춰 전략을 바꾼다.

여러 체크포인트를 넘기거나 실패가 발생해 재개 연속성이 필요할 때만 `codex-goals/goal-member-workbench-activation-20260815-1154.progress.md`를 만들고, 각 항목에 시각/체크포인트, 변경 또는 실험, 직접 증거와 결과, keep/revert/revise 결정, 남은 일과 blocker를 짧게 기록한다.

## Practical verification contract

- 요청된 결과를 테스트, 하니스, validator, 인증서, 문서만으로 대체하지 않는다.
- 실제 사용자가 들어가는 UI와 기본 제어 경로를 통해 최소 한 번 대표 흐름을 검증한다.
- 사용자에게 보이는 결과를 가장 직접적으로 보여주는 기존 인터페이스를 우선한다.
- mock, fixture, replay, 하위 API, readback, 내부 검사는 진단을 보조할 수 있지만 실제 흐름 검증을 대체하지 않는다.
- 선호 도구나 환경이 없으면 전체 작업을 중단하지 말고, 제어 흐름을 보존하는 가장 가까운 인터페이스로 진행한다.
- 실제 흐름에서 결함이 드러나면 근본 원인을 수정하고 가장 작은 회귀 테스트를 추가한 뒤 같은 실제 흐름을 다시 실행한다.
- 변경 범위에 맞는 검사부터 시작하고, 의존성 영향·공유 인프라·프로젝트 정책·관찰된 증거가 정당화할 때만 범위를 넓힌다.
- 더 많은 검증 장치를 만드는 것보다 제품을 고치고 사용자 흐름을 다시 실행하는 것을 우선한다.
- 요청 결과를 충분히 입증하는 직접 증거가 모이면 검증을 멈춘다. 확신을 꾸미기 위해 불필요한 테스트·커버리지·문서·중복 validator를 추가하지 않는다.

## Delivery and evidence

- 구현 시 변경 파일은 회원 내비게이션·주식 워크벤치·권한 경계와 직접 관련된 파일로 제한한다. 필요한 회귀 테스트와 사용자 상태 문구도 같은 범위에 포함한다.
- 최종 산출물은 변경된 코드와 테스트, 실제 UI 검증 메모 또는 스크린샷, 실행한 명령과 결과, 잔여 한계 목록이다.
- 변경이 없고 대표 승인에서 멈춘 경우에도 조사 결과, 선택지, 직접 증거와 정확한 승인 필요 지점을 보고한다. 조사 문서를 임의로 제품 방향 확정 문서처럼 포장하지 않는다.
- 중단 후 재개 가능성이 생길 때만 위의 `.progress.md` companion log를 유지한다. 긴 원시 로그와 민감정보는 넣지 말고 경로와 요약 결과만 기록한다.
- 완료 보고에는 목표와 완료 조건 대비 결과, 실제 사용자 흐름의 직접 증거, 중요한 변경과 실무 영향, 실제 실행한 검사, 미검증 한계 또는 blocker, 해당하는 artifact 식별자를 포함한다.

## Hard pause conditions

다음 중 하나가 사실이고 안전한 독립 작업도 남지 않을 때만 일시정지한다.

- 필요한 접근권한·자격증명·환경·외부 서비스가 없다.
- 다음 행동이 파괴적·되돌릴 수 없음·보안을 약화함·중대한 비용 발생·운영 영향이 있고 명확한 승인이나 정책 근거가 없다.
- 권위 있는 출처가 충돌하고 선택이 사용자 가치·준수·데이터 의미·제품 정책을 바꾼다.
- 회원 제품과 관리자 콘텐츠 운영의 노출 정책처럼 사람이 결정해야 하는 제품·법률·보안·사업 판단을 안전하게 추론할 수 없다.
- 저장소 보호·CI·리뷰·배포 정책이 사람의 행동을 요구한다.

일시정지할 때는 정확한 blocker, 근거, 완료한 독립 작업, 가장 안전한 다음 행동, 필요한 최소 대표 결정을 보고한다. “명확화 필요”라고만 쓰지 않는다.
