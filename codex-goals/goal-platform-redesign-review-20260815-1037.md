# Codex Goal Contract — Jay AI Platform 개편 검토 보고서

이 파일은 완전한 영속형 목표 계약서다. 작업 전에 전체를 읽고, 이전 채팅 기록에 의존하지 말며, 아래 완료 조건이 충족되거나 하드 일시정지 조건이 발생할 때까지 자율적으로 진행한다.

## Goal

Jay AI Platform의 실제 사용자 흐름, 코드 구조, 운영 경계를 근거로 검토하여, 대표가 다음 개편의 제품 방향과 첫 구현 단위를 결정할 수 있는 `docs/JAY_AI_PLATFORM_REDESIGN_REVIEW.md`를 완성한다. 이 목표는 제품을 개편하는 구현 작업이 아니라, 회원용 주식 SaaS와 대표 전용 콘텐츠 운영 도구의 경계를 명확히 하고 검증 가능한 개편 권고안을 만드는 일이다.

## User problem and value

- **주 사용자:** Jay AI Platform의 대표 겸 운영자이며, 향후 회원용 서비스를 운영할 사람이다.
- **사용 상황:** 신규 기능을 계속 추가하거나 VPS에 배포하기 전에, 현재 제품이 누구에게 어떤 가치를 주는지와 다음 개발 순서를 판단해야 한다.
- **핵심 문제:** 회원용 한국 주식 분석·리포트·결제 기능과 대표 전용 YouTube/이모티콘 콘텐츠 파이프라인 뷰어가 하나의 대시보드에 공존한다. 기능은 존재하지만 제품의 핵심 사용자, 정보 구조, 수익 모델 우선순위, 콘텐츠 운영 도구의 귀속 경계가 한눈에 결정되지 않는다.
- **완료 가치:** 대표가 유지·분리·보류할 영역, 목표 사용자 흐름, MVP 이후 단계, 위험과 의사결정 지점을 한 문서에서 검토하고 다음 구현 Goal을 안전하게 발행할 수 있다.
- **가장 중요한 현재 공백:** 현재 화면과 README의 기능 나열은 있으나, 실제 흐름에서 검증된 제품 범위와 일관된 개편 목표 정보 구조가 없다.

### 미확인 사항과 확인 방법

- **미확인:** 현재 VPS 배포 상태, 실제 결제 키·OpenDART 키·OpenAI 키의 설정 여부, 실제 회원/결제 데이터, 운영 사용자 수와 우선 고객. 비밀값이나 운영 DB를 열지 말고, 필요하면 대표에게 요약 상태만 요청하거나 공개된 비밀 없는 배포 로그/설정 문서만 검토한다.
- **미확인:** 로컬에서 실제 UI가 현재 선행 변경까지 포함해 정상 동작하는지. 별도 임시 `DATA_DIR`로 로컬 서버를 기동하고 브라우저에서 대표 흐름을 확인한다. `backend/data/*.db`는 사용·수정·삭제하지 않는다.
- **추론:** 제품 개편의 핵심은 기능 개수 확대보다 주 사용자와 제품 경계의 정리다. 이 추론은 위의 회원용/대표 전용 기능 혼재 증거에 기반하며, 실제 흐름과 문서 근거로 검증하거나 반박해야 한다.

## Constraints

### 범위

- 코드, 스키마, UI, 배포 설정을 변경하지 않고 현 상태를 검토한다.
- 새 산출물은 `docs/JAY_AI_PLATFORM_REDESIGN_REVIEW.md`와, 중단 후 재개 가능성이 실제로 생길 때만 `codex-goals/goal-platform-redesign-review-20260815-1037.progress.md`로 제한한다.
- 검토 보고서는 기능/흐름 인벤토리, 사용자·가치 가설, 현재 정보 구조 문제, 최소 세 가지 개편 선택지 비교, 권고 목표 정보 구조, 유지·분리·보류 표, 첫 구현 Goal 후보와 순서, 리스크·미확인 가정을 포함한다.
- `content/`의 개인 제작 파이프라인과 앱의 콘텐츠 운영 뷰어가 어떤 관계여야 하는지를 반드시 검토하되, 파이프라인 산출물 자체를 편집하지 않는다.

### 비범위

- FastAPI/React/SQLite 코드 변경, DB 마이그레이션, 결제·OpenDART·OpenAI 실제 호출, 사용자 데이터 수정, 배포, 커밋, push, PR, 병합, VPS 작업은 범위 밖이다.
- 투자 조언·매수/매도 권고의 적법성 결론, 결제/구독 가격 확정, 개인정보·법률 자문 결론은 내리지 않는다. 필요한 검토 사항과 보수적 경계만 기록한다.
- 대표 개인 콘텐츠의 대본·이미지·이모티콘 제작 또는 외부 플랫폼 제출은 수행하지 않는다.

### 보호 규칙

- 기존 미커밋 변경은 타인의 진행 작업일 수 있다. 되돌리거나 포맷하거나 스테이징하지 말고, 보고서에 관찰 사실로만 다룬다.
- 비밀값, 토큰, 개인식별정보, 원시 운영 데이터, `.env` 내용은 열거나 보고서에 넣지 않는다. 환경변수 이름만 필요할 때 언급한다.
- SQLite 스키마 변경이 후속 Goal에서 필요해도 `services/*.py`의 `CREATE TABLE IF NOT EXISTS`와 `ensure_column()` 패턴 및 무손실 원칙을 지켜야 한다. 이 검토 Goal에서는 적용하지 않는다.
- `main`에 대한 push는 실제 배포가 될 수 있다. 대표의 이번 요청에는 그러한 권한이 없다.

## Done when

`docs/JAY_AI_PLATFORM_REDESIGN_REVIEW.md`가 완성되어 **AND** (1) 코드와 브라우저의 대표 흐름에 근거한 현재 기능·경계 인벤토리, (2) 회원용 주식 제품과 대표 전용 콘텐츠 운영의 유지/분리/보류 결정 기준 및 최소 세 가지 선택지 비교, (3) 권고하는 목표 사용자·정보 구조·첫 구현 단위·측정 기준, (4) 검증된 사실/추론/미확인을 구분한 위험·의사결정 목록을 담고, **AND** 보고서의 모든 중요한 주장에 관련 파일 또는 직접 관찰 증거가 연결되었을 때 이 Goal을 완료한다.

대표 흐름은 다음을 실제 로컬 인터페이스에서 확인한다.

1. 비로그인 방문자가 앱을 열어 로그인/가입 진입점을 볼 수 있다.
2. 임시 데이터 디렉터리의 테스트 계정으로 가입·로그인한 사용자가 한국 주식 화면의 보유종목, 관심종목, 분석, 후보 스캔, 공시/리포트/수익화 진입 구조를 볼 수 있다. 실제 주가·공시·AI·결제 외부 호출은 실행하지 않는다.
3. 같은 임시 계정을 최초 관리자 계정으로 사용해 관리자/콘텐츠 운영 화면의 접근 경계와 YouTube 읽기 전용 흐름을 확인한다. 이모티콘 UI/API는 미커밋 WIP로 구분해, 호출 실패 여부만 관찰하고 코드를 고치지 않는다.

직접 증거는 로컬 브라우저 관찰 메모(민감정보 제외), 관련 API 응답/화면 상태, 보고서 내 파일 경로, 그리고 실행한 명령의 성공·실패 결과다. 회귀 경계는 현 작업 트리의 선행 변경과 `backend/data/*.db`를 전혀 변경하지 않는 것이다. 잔여 제한은 실제 운영 사용자 인터뷰, 운영 지표, 실결제, VPS 배포는 이 Goal에서 검증하지 않는다는 점이다.

## Execution checkpoints

1. **근거 있는 기준선 만들기** — 루트 `AGENTS.md`, README, `backend/app/main.py`, 라우터/서비스/스키마, `frontend/src/App.tsx`, 관련 컴포넌트·테스트, `git status`, `git diff --stat`, 최근 커밋을 읽어 기능 인벤토리와 WIP 경계를 기록한다. 증거는 파일 경로와 명령 출력이다. 선행 조건은 미커밋 변경을 건드리지 않는 것이다.
2. **대표 흐름 관찰하기** — 안전한 임시 데이터 디렉터리와 로컬 서버로 위 세 흐름을 브라우저에서 확인하고, 화면 진입·권한·실패 상태를 기록한다. 증거는 민감정보 없는 관찰 메모와 필요 최소한의 화면 캡처/콘솔 오류 요약이다. 선행 조건은 임시 런타임이 `backend/data`와 실제 외부 결제를 건드리지 않는 것이다.
3. **개편 대안과 권고안 만들기** — 현 기능을 사용자 가치, 운영 부담, 경계 일관성, 구현 위험, 수익화 검증 가능성으로 비교한다. 최소 세 가지 상호 배타적인 개편 방향과 각 방향의 장단점·의존성·보류 기능을 작성하고, 가장 작은 다음 구현 단위를 권고한다. 증거는 앞 두 체크포인트의 파일/흐름 근거다.
4. **의사결정용 보고서 검증하기** — 보고서가 혼자 읽혀도 현황, 근거, 선택지, 권고, 결정을 보류할 사안, 첫 후속 Goal을 답하는지 냉독한다. 비밀·운영 데이터·채팅 의존 문구가 없는지, 코드가 변경되지 않았는지 `git diff --name-only`로 확인한다. 선행 조건은 모든 주요 권고에 근거 또는 명시된 가정이 있어야 한다.

새 증거가 전제를 반박하면 체크포인트 순서와 가설은 변경할 수 있다. 변경 이유를 보고서 또는 진행 로그에 남긴다.

## Autonomous decision contract

- 사용자가 부재하다고 가정하고, 가역적이고 안전한 조사·로컬 관찰·검토 보고서 작성은 즉시 진행한다.
- 결정은 이 Goal, 사용자 가치, 현 코드, 프로젝트 규칙, 테스트, 런타임 증거, 커밋 이력에 기반한다.
- 제품의 핵심 고객과 경계에 관해 되돌릴 수 없는 결론을 확정하지 않는다. 보고서는 근거 있는 권고를 내되, 가격·법률·생산 배포·회원 데이터 의미를 바꾸는 결정은 대표 판단 항목으로 표시한다.
- 한 확인 경로가 막혀도 파일·테스트·다른 로컬 인터페이스 등 독립된 근거 수집을 계속한다. 다만 공통 원인(예: 서버 기동 불가)이 의심되면 무의미한 재시도를 하지 않는다.
- 이번 요청이 허용하는 것은 작업공간 읽기, 안전한 임시 로컬 실행, 검토 문서와 필요한 진행 로그 작성뿐이다. 커밋, push, PR, 병합, 배포, 운영 변경, 외부 결제/외부 API 호출은 허용되지 않는다.
- 접근 불가나 설정 누락을 성공으로 보고하지 않는다. 선행 미커밋 변경은 유지하며, 진행을 단순화하려고 삭제·덮어쓰기·스테이징하지 않는다.
- 테스트, 보안, 리뷰, CI, 배포 제어를 삭제·약화·우회하지 않는다.

## Recursive improvement and failure recovery

목표와 권위 있는 출처는 고정하되, 가설·분해·검토 방식·검증 방식은 증거에 따라 수정한다. 이전 실패는 현재 확인되지 않았으므로 가공해 기록하지 않는다.

흐름 관찰 또는 경계 판정이 실패·정체될 때는 반복 가정과 실제 사용자 흐름을 우회한 증거를 먼저 찾는다. 이후 아래처럼 구조적으로 다른 접근을 비교한다.

1. **회원용 투자 정보 제품 집중:** 콘텐츠 운영을 앱에서 제거하거나 별도 내부 운영 도구로 분리하고, 주식 분석→리포트→Pro 가치 검증을 핵심 흐름으로 한다. 성공 가능성은 중간~높음(60–80%): 이미 가장 많은 회원용 기능이 존재하지만 투자·결제 검증과 규제 경계를 더 확인해야 한다.
2. **이중 표면의 모듈형 운영 플랫폼:** 회원용 주식 제품과 대표 전용 콘텐츠 운영을 명확히 분리된 역할/정보 구조 아래 유지한다. 성공 가능성은 중간(40–65%): 현재 코드 재사용은 크지만 제품 메시지와 운영 복잡도가 높다.
3. **대표 운영 도구 집중:** 콘텐츠 제작·성과 관리 흐름을 핵심으로 재정의하고 주식 기능을 실험/보류 영역으로 격리한다. 성공 가능성은 낮음~중간(25–50%): 실제 개인 파이프라인 근거는 있으나 `AGENTS.md`는 이를 앱 회원 기능이 아니라고 명시하고 있어 별도 제품화 근거가 필요하다.

가장 적은 비용으로 가장 많은 정보를 주는 실험을 선택한다. 예를 들어 화면 관찰로도 경계 혼재가 확인되면 기능을 더 구현하지 않고, 보고서의 정보 구조 비교를 먼저 끝낸다. 매 반복 후 새로 확인된 사실, 틀린 가정, 변경 전제 없이는 반복하지 않을 방법, 최대 병목, 다음 실험을 진행 로그에 기록한다. 같은 실패를 단순 재시도로 반복하지 않는다.

## Practical verification contract

- 이 Goal의 요청 결과는 제품 개편이 아니라 의사결정 가능한 검토다. 테스트나 문서만으로 앱 기능이 정상이라고 대체 주장하지 말고, 위의 실제 브라우저 흐름을 최소 한 번 확인한다.
- 브라우저를 사용할 수 없으면 `scripts/start-local-dev.ps1`의 동작, FastAPI의 인증된 API, 기존 UI 테스트를 가장 가까운 대체 근거로 사용하되, 보고서에 브라우저 미검증 사실과 이유를 명시한다.
- 임시 로컬 런타임에서만 테스트 가입/로그인을 수행한다. 데이터 디렉터리는 명시적으로 별도 경로로 설정하고, 정리 전 대상 경로가 임시 디렉터리인지 확인한다.
- 실제 흐름에서 결함을 발견해도 이 Goal에서 고치지 않는다. 재현 단계·관찰 결과·영향·권고 후속 Goal로 기록한다.
- 관련 범위부터 확인하며, 코드가 바뀌지 않았으면 전체 테스트를 의례적으로 실행하지 않는다. 흐름 또는 기존 계약이 모순될 경우에만 관련 백엔드 pytest와 프론트 `npm run verify`를 실행하고, 실제 실행 결과만 기록한다.

## Hard pause conditions

다음 중 하나가 사실이고 안전한 독립 작업도 남지 않을 때만 일시정지한다.

- 로컬 서버·브라우저·필요 의존성을 사용할 수 없고 코드·테스트·문서만으로도 더 이상 근거를 수집할 수 없다.
- 다음 행동이 운영 DB 수정, 실제 결제/외부 API 호출, 배포, push, 파괴적 정리, 보안 약화, 비용 발생을 요구하지만 명시 권한이 없다.

- 가격, 투자 규제, 법률, 개인정보, 실제 고객 우선순위처럼 대표만 결정할 수 있는 선택이 권고의 전제인데 대안 제시도 불가능하다.

일시정지 시 정확한 blocker, 근거, 완료한 독립 작업, 가장 안전한 다음 행동, 필요한 최소 대표 결정을 보고한다. “명확화 필요”처럼 모호하게만 쓰지 않는다.
